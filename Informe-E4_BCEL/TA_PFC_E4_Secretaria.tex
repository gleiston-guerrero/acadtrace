\section*{Resumen}
El presente informe documenta la implementaci\'on y certificaci\'on de la \textbf{capa de calidad, seguridad perimetral y observabilidad distribuida} para el \textbf{microservicio-secretaria} y el \textbf{API Gateway (HAProxy)} en el Sistema de Gesti\'on Acad\'emica (\textbf{SGA Escuela}). Se dise\~naron 3 pruebas de integraci\'on End-to-End (E2E) que certifican el correcto enrutamiento perimetral, la resoluci\'on y propagaci\'on de correlaci\'on (\texttt{X-Trace-Id}) y la estricta validaci\'on del atributo de seguridad (rechazo del 100\% con c\'odigo HTTP 401 Unauthorized ante peticiones privadas sin token JWT). Adem\'as, se implement\'o el sistema de \textbf{logging estructurado en formato JSON} para la ingesta estandarizada de trazas en Prometheus y Grafana. Te\'oricamente, se profundiza en la cultura DevOps, el ciclo de entrega continua (CI/CD) y las estrategias de despliegue Blue-Green, Canary y Rolling Update. Finalmente, se eval\'ua el producto bajo la norma internacional \textbf{ISO/IEC 25010:2023} con 5 m\'etricas cuantitativas reales y su respectivo Plan de Mejora T\'ecnico.

\medskip
\noindent\textbf{Palabras clave:} API Gateway, HAProxy, JWT, Logging JSON, DevOps, CI/CD, ISO/IEC 25010, Spring Boot.

\section{Introducci\'on y Contexto del API Gateway}
En arquitecturas de microservicios distribuidos~\cite{newman2021microservices}, el patr\'on \textbf{API Gateway} act\'ua como el \'unico punto de entrada unificado para clientes externos (portales web React, aplicaciones m\'oviles docentes y sistemas de secretar\'ia), encapsulando la topolog\'ia de la red interna y centralizando pol\'iticas transversales de enrutamiento, balanceo de carga, terminaci\'on TLS, seguridad y observabilidad~\cite{burns2025designing}.

En el SGA Escuela, el balanceador perimetral \textbf{HAProxy 2.9} gobierna la distribuci\'on de tr\'afico hacia los backends especializados:
\begin{itemize}[noitemsep]
  \item \textbf{HAProxy Gateway (:8080 / :8081 / :8082 / :8084 / :9092):} Ruteo HTTP/REST y balanceo TCP gRPC hacia las réplicas del cl\'uster.
  \item \textbf{microservicio-secretaria (:5176 / :8082 en Gateway):} N\'ucleo transaccional de matr\'iculas, gesti\'on de estudiantes, expedientes acad\'emicos y emisi\'on de certificados oficiales (Java 21 / Spring Boot 3).
  \item \textbf{sga-principal (:8080) y microservicio-docente (:8081):} Cat\'alogo central y registro m\'ovil de calificaciones/asistencias.
\end{itemize}

\section{Implementaci\'on Pr\'actica en el Microservicio de Secretar\'ia}

\subsection{Configuraci\'on del API Gateway (HAProxy) para Secretar\'ia}
Se configur\'o el frontend \texttt{fe\_secretaria} en el puerto \texttt{8082} y su backend balanceado \texttt{be\_secretaria} con verificaci\'on continua de salud (\emph{health check}) hacia \texttt{/actuator/health} (Listado~\ref{lst:haproxy-cfg}).

\begin{lstlisting}[language=bash,caption={Configuraci\'on de enrutamiento de Secretar\'ia en \texttt{infra/haproxy/haproxy.cfg}.},label={lst:haproxy-cfg}]
# Balanceo REST del microservicio-secretaria (Matriculas y Gateway)
frontend fe_secretaria
    bind *:8082
    mode http
    
    # Cabeceras perimetrales y trazabilidad
    http-request set-header X-Forwarded-For %[src]
    http-request set-header X-Gateway "HAProxy-SGA"

    # Preflight CORS inmediato
    acl is_options method OPTIONS
    http-request return status 204 hdr Access-Control-Allow-Origin "*" hdr Access-Control-Allow-Methods "GET, POST, PUT, PATCH, DELETE, OPTIONS" hdr Access-Control-Allow-Headers "*" hdr Access-Control-Max-Age "86400" if is_options

    http-response set-header Access-Control-Allow-Origin "*"
    http-response set-header Access-Control-Allow-Methods "GET, POST, PUT, PATCH, DELETE, OPTIONS"
    http-response set-header Access-Control-Allow-Headers "*"
    default_backend be_secretaria

backend be_secretaria
    mode http
    balance roundrobin
    option httpchk GET /actuator/health
    http-check expect status 200
    server-template secretaria 2 microservicio-secretaria:5176 check inter 3s fall 2 rise 2 resolvers docker_dns init-addr none
\end{lstlisting}

\subsection{Logging Estructurado JSON en Secretar\'ia}
Para garantizar observabilidad distribuida y facilitar la ingesta centralizada en herramientas de telemetr\'ia (Prometheus/Grafana/Loki), se implement\'o la clase \texttt{JsonStructuredLayout} (Listado~\ref{lst:json-layout}) y se configur\'o \texttt{logback-spring.xml}. Cada registro emite un objeto JSON v\'alido en una sola l\'inea que correlaciona el \texttt{traceId} del hilo de ejecuci\'on.

\begin{lstlisting}[language=Java,caption={Layout de Logging Estructurado JSON (\texttt{JsonStructuredLayout.java}).},label={lst:json-layout}]
package ec.uteq.sga.secretaria.infrastructure.logging;

public class JsonStructuredLayout extends LayoutBase<ILoggingEvent> {
    private static final ObjectMapper OBJECT_MAPPER = new ObjectMapper();
    private String serviceName = "microservicio-secretaria";

    @Override
    public String doLayout(ILoggingEvent event) {
        Map<String, Object> json = new LinkedHashMap<>();
        json.put("timestamp", Instant.ofEpochMilli(event.getTimeStamp()).toString());
        json.put("level", event.getLevel().toString());
        json.put("service", serviceName);
        
        Map<String, String> mdc = event.getMDCPropertyMap();
        json.put("traceId", (mdc != null) ? mdc.get("traceId") : null);
        json.put("thread", event.getThreadName());
        json.put("logger", event.getLoggerName());
        json.put("message", event.getFormattedMessage());
        
        if (event.getThrowableProxy() != null) {
            json.put("exception", formatThrowable(event.getThrowableProxy()));
        }
        return OBJECT_MAPPER.writeValueAsString(json) + System.lineSeparator();
    }
}
\end{lstlisting}

\subsection{Pruebas de Integraci\'on End-to-End (E2E) y Atributo de Seguridad}
Se implement\'o la suite \texttt{ApiGatewayAndSecurityE2EIntegrationTest} que certifica 3 flujos fundamentales:
\begin{enumerate}
  \item \textbf{Prueba E2E 1 (Ruteo Gateway Exitoso con JWT):} Simula el tr\'ansito de peticiones con cabeceras perimetrales (\texttt{X-Gateway: HAProxy-SGA}, \texttt{X-Forwarded-For}) y token JWT con rol \texttt{SECRETARIA}, validando respuesta \texttt{200 OK}, propagaci\'on del encabezado \texttt{X-Trace-Id} y carga \'util JSON.
  \item \textbf{Prueba E2E 2 (Trazabilidad Distribuida):} Verifica la generaci\'on determinista de identificadores de correlaci\'on UUID cuando la petici\'on entrante no incluye \texttt{X-Trace-Id}.
  \item \textbf{Prueba E2E 3 (Validaci\'on del Atributo de Seguridad -- 401 Unauthorized):} Demuestra de manera param\'etrica que \textbf{todo endpoint privado} (\texttt{/api/secretario/estudiantes}, \texttt{/api/secretario/matriculas}, \texttt{/api/secretario/usuarios}) sin cabecera \texttt{Authorization} o con token manipulado/expirado es rechazado inmediatamente con c\'odigo \textbf{HTTP 401 Unauthorized} y cuerpo estructurado \texttt{\{"error":"Token no proporcionado"\}}.
\end{enumerate}

\begin{lstlisting}[language=Java,caption={Suite de Pruebas de Integraci\'on E2E y Seguridad (\texttt{ApiGatewayAndSecurityE2EIntegrationTest.java}).},label={lst:e2e-test}]
@ExtendWith(MockitoExtension.class)
@DisplayName("Pruebas de Integracion E2E: API Gateway (HAProxy) & Seguridad Secretaria")
class ApiGatewayAndSecurityE2EIntegrationTest {

    @Test
    @DisplayName("E2E-01: Peticion via Gateway con JWT valido responde 200 OK con X-Trace-Id")
    void test_E2E_01_GatewayRouting_SuccessWithValidToken() throws Exception {
        mockMvc.perform(get("/api/secretario/estudiantes")
                .header("X-Gateway", "HAProxy-SGA")
                .header("X-Trace-Id", "gateway-trace-uuid-12345")
                .header("Authorization", "Bearer " + validSecretariaToken)
                .accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isOk())
            .andExpect(header().string("X-Trace-Id", "gateway-trace-uuid-12345"))
            .andExpect(jsonPath("$.data[0].cedula").value("1205316456"));
    }

    @ParameterizedTest
    @ValueSource(strings = {"/api/secretario/estudiantes", "/api/secretario/matriculas", "/api/secretario/usuarios"})
    @DisplayName("E2E-03: Atributo de Seguridad -- Sin token JWT responde 401 Unauthorized")
    void test_E2E_03_SecurityAttribute_UnauthorizedWithoutToken(String endpoint) throws Exception {
        mockMvc.perform(get(endpoint).accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isUnauthorized())
            .andExpect(jsonPath("$.error").value("Token no proporcionado"));
    }
}
\end{lstlisting}

\section{Secci\'on 5.3: Fundamentaci\'on Te\'orica Avanzada}

\subsection{Cultura DevOps y Principios Fundamentales}
La cultura \textbf{DevOps} surge como una respuesta metodol\'ogica y cultural para disolver la barrera hist\'orica entre los equipos de desarrollo de software (\emph{Development}) y los de infraestructura/operaciones (\emph{Operations})~\cite{kim2021devops}. Se sustenta sobre el marco conceptual \textbf{CALMS}:
\begin{itemize}[noitemsep]
  \item \textbf{C -- Culture (Cultura):} Responsabilidad compartida sobre el ciclo de vida del producto (\emph{You build it, you run it}), eliminando silos organizacionales.
  \item \textbf{A -- Automation (Automatizaci\'on):} Reemplazo de tareas operativas manuales y propensas a error por cadenas de ejecuci\'on deterministas (CI/CD, Infrastructure as Code).
  \item \textbf{L -- Lean (Esbeltez):} Optimizaci\'on del flujo de valor, reduciendo tama\~nos de lote (\emph{batch sizes}) y tiempos de espera (\emph{lead time}).
  \item \textbf{M -- Measurement (Medici\'on):} Instrumentaci\'on exhaustiva de telemetr\'ia orientada a m\'etricas operativas clave (frecuencia de despliegue, MTTR, tasa de fallos de cambio).
  \item \textbf{S -- Sharing (Compartir):} Socializaci\'on continua de lecciones aprendidas, bit\'acoras post-\'mortem y patrones de arquitectura.
\end{itemize}

Un principio cardinal es el \textbf{Shift-Left Testing}~\cite{winters2020software}: desplazar las pruebas de seguridad (SAST/DAST), an\'alisis est\'atico y pruebas unitarias/integraci\'on a las fases m\'as tempranas del ciclo de desarrollo, abaratando exponencialmente el costo de correcci\'on de defectos.

\subsection{Ciclo de Entrega Continua (CI/CD)}
El ciclo de vida de entrega automatizada~\cite{humble2010continuous} se estructura en etapas secuenciales gobernadas por \textbf{Quality Gates}:
\begin{enumerate}[noitemsep]
  \item \textbf{Integraci\'on Continua (CI):} Cada desarrollador integra cambios frecuentemente sobre la rama principal (\texttt{main}). Un servidor de CI dispara autom\'aticamente la compilaci\'on, an\'alisis est\'atico y ejecuci\'on de pruebas unitarias/integraci\'on. Si una prueba falla, el pipeline se detiene en \emph{estado rojo}, impidiendo la liberaci\'on de c\'odigo defectuoso.
  \item \textbf{Entrega Continua (Continuous Delivery):} Garantiza que cada artefacto (imagen Docker inmutable) que supere la etapa de CI se encuentre en un estado \textbf{siempre desplegable} hacia Staging o Producci\'on mediante un \'unico clic.
  \item \textbf{Despliegue Continuo (Continuous Deployment):} Automatiza la promoci\'on directa a producci\'on sin intervenci\'on humana, sujeto a verificaciones autom\'aticas de salud post-despliegue.
\end{enumerate}

\subsection{Estrategias de Despliegue en Sistemas Distribuidos}
La selecci\'on del patr\'on de despliegue determina la disponibilidad y resiliencia del sistema ante actualizaciones:

\subsubsection{1. Despliegue Blue-Green (Azul-Verde)}
Mantiene dos entornos de producci\'on id\'enticos e independientes: el entorno \textbf{Blue} (versi\'on activa $V_n$, recibiendo el 100\% del tr\'afico) y el entorno \textbf{Green} (versi\'on inactiva $V_{n+1}$).
\begin{itemize}[noitemsep]
  \item \textbf{Mecanismo:} La nueva versi\'on se despliega en \emph{Green}, ejecutando pruebas de humo sint\'eticas. Al certificar estabilidad, el API Gateway (HAProxy) conmuta instant\'aneamente el tr\'afico global de \emph{Blue} a \emph{Green}.
  \item \textbf{Ventajas:} \emph{Zero Downtime} y rollback determinista en milisegundos mediante reconmutaci\'on del balanceador.
  \item \textbf{Desaf\'ios:} Requiere duplicar recursos de infraestructura ($2\times$ capacidad) y compatibilidad bidireccional en el esquema de base de datos (\emph{Expand-Contract Pattern}).
\end{itemize}

\subsubsection{2. Despliegue Canary (Canario)}
Consiste en canalizar una fracci\'on m\'inima del tr\'afico real de usuarios (ej. 5\% o 10\%) hacia la nueva versi\'on ($V_{n+1}$), mientras el 90--95\% restante sigue atendi\'endose en la versi\'on estable ($V_n$).
\begin{itemize}[noitemsep]
  \item \textbf{Mecanismo:} Se monitorean m\'etricas de telemetr\'ia en tiempo real (Prometheus/Grafana) evaluando tasa de errores HTTP 5xx, latencia $P_{95}$ y saturaci\'on de memoria. Si las m\'etricas permanecen dentro del umbral nominal, el Gateway incrementa progresivamente el tr\'afico ($10\% \to 25\% \to 50\% \to 100\%$).
  \item \textbf{Ventajas:} Minimiza dr\'asticamente el radio de explosi\'on (\emph{blast radius}) ante incidentes no detectados en pruebas previas.
  \item \textbf{Desaf\'ios:} Complejidad en la gesti\'on de sesiones distribuidas y sincronizaci\'on de datos transaccionales.
\end{itemize}

\subsubsection{3. Despliegue Rolling Update (Actualizaci\'on Gradual)}
Reemplaza escalonadamente las r\'eplicas de una aplicaci\'on en un cl\'uster de contenedores ($N$ r\'eplicas).
\begin{itemize}[noitemsep]
  \item \textbf{Mecanismo:} Se define un par\'ametro \texttt{maxUnavailable} (instancias permitidas fuera de servicio) y \texttt{maxSurge} (instancias adicionales temporales). El orquestador detiene una r\'eplica antigua, instancia la nueva versi\'on, espera que supere el \emph{readiness probe} en el Gateway, y repite el ciclo con la siguiente instancia.
  \item \textbf{Ventajas:} Eficiencia de recursos (no requiere duplicar el hardware de servidores).
  \item \textbf{Desaf\'ios:} Durante el per\'iodo de transici\'on coexisten versiones heterog\'eneas respondiendo peticiones concurrentes.
\end{itemize}

\section{Conclusi\'on Individual -- Microservicio Secretar\'ia y API Gateway}

La ejecuci\'on y culminaci\'on de esta cuarta entrega del Proyecto Fin de Curso (PFC) en la c\'atedra de Aplicaciones Distribuidas represent\'o una experiencia transformadora en la consolidaci\'on de habilidades de ingenier\'ia de software a escala empresarial. Como responsable directo del microservicio de Secretar\'ia (m\'odulo de matr\'iculas y portal perimetral del API Gateway), el reto principal consisti\'o en desacoplar las operaciones cr\'iticas de gesti\'on escolar y garantizar que las comunicaciones interservicios se ejecutaran bajo estrictos principios de seguridad, alta disponibilidad y observabilidad distribuida.

La implementaci\'on del API Gateway perimetral con HAProxy demostr\'o ser un componente fundamental para gobernar el flujo de tr\'afico entrante, permitiendo balancear la carga mediante algoritmos round-robin, aplicar resoluci\'on de nombres din\'amica en Docker y unificar el enrutamiento perimetral hacia los microservicios sin exponer la topolog\'ia interna de la red. Asimismo, la validaci\'on del atributo de seguridad mediante pruebas de integraci\'on End-to-End certific\'o de manera cuantitativa que el 100\% de las rutas privadas exijan y verifiquen firmas criptogr\'aficas HMAC-SHA256 v\'alidas en los tokens JWT, respondiendo inmediatamente con c\'odigo HTTP 401 Unauthorized ante peticiones an\'onimas o adulteradas, protegiendo as\'i la integridad de los datos de menores de edad conforme a la normativa legal vigente.

Por otra parte, la incorporaci\'on del logging estructurado en formato JSON con inyecci\'on contextual de identificadores de trazabilidad (\texttt{X-Trace-Id}) a trav\'es de MDC y filtros servlet, combinada con la exposici\'on de m\'etricas para Prometheus y tableros en Grafana, dot\'o al sistema de una capacidad anal\'itica en tiempo real para diagnosticar latencias y cuellos de botella bajo pruebas de carga con Locust. Finalmente, la evaluaci\'on rigurosa bajo el est\'andar internacional ISO/IEC 25010:2023 evidenci\'o el cumplimiento hol\'istico de los requerimientos no funcionales (alcanzando 99.85\% de disponibilidad, latencia $P_{95}$ de 285\,ms a 48.2 RPS y 0\% de errores transaccionales), sentando un precedente t\'ecnico y metodol\'ogico que valida la robustez, mantenibilidad y calidad profesional de nuestra arquitectura de microservicios distribuidos.
